# 実装ロードマップと評価基準

## 1. 実施方針

最初から完成外観を作らず、寸法と構造を段階的に固定する。
各段階で機械検査と6方向の目視検査を行い、合格してから細部へ進む。

## 2. フェーズ構成

### P0：基準寸法と入力の確定

目的：絶対スケールと写真の向きを決める。

作業：

1. 6枚の元画像、切抜き、画像ハッシュをmanifestへ記録する。
2. 前方向、左右、上下の対応を再確認する。
3. 対角または左右のモーター中心間距離を実測する。
4. 可能なら全幅、全長、全高、プロペラ直径、ガード外径、総質量を測る。
5. `config/drone2_model.yaml`の初版を作る。

合格条件：

- 基準寸法が1個以上ある。
- 4個のモーター中心を写真上で特定できる。
- 前後左右の定義が確定している。
- 未確定値が`null`または`placeholder`として明示されている。

基準寸法がない場合は、比率Blockoutへ進めるが、物理モデルとしてはP0不合格のままとする。

### P1：6方向参照シーン

目的：写真と生成モデルを同じBlenderシーンで比較できるようにする。

作業：

1. 上、下、前、後、左、右の正投影カメラを作る。
2. 各写真をCamera Backgroundまたは参照面へ設定する。
3. モーター中心と機体中心を使って写真ごとの倍率・位置・回転を合わせる。
4. 補正値を設定ファイルへ保存する。
5. 参照だけを含む`.blend`と6方向プレビューを出力する。

合格条件：

- 4個のモーター中心が上面または下面写真と整列する。
- 左右写真の全高基準が一致する。
- 各写真の補正値を再読込みして同じ表示を再現できる。

### P2：構造Blockout

目的：細部を除いた主要部品と外形を作る。

生成する部品：

- 中央ボディ
- アーム4本
- モーターハウジング4個
- 簡易プロペラ4個
- 簡易ガード4個

この段階では無彩色とし、材質や小部品を作らない。

合格条件：

- 設定値とBlender実測寸法の差が0.5 mm以内。
- 4個のモーター中心位置が設定値と0.5 mm以内で一致する。
- 部品数、名前、親子階層が規約どおりである。
- 6方向すべてで、主要輪郭が写真の許容帯に入る。
- ローター原点と回転軸が正しい。

### P3：外形フィッティング

目的：写真で識別できる外装形状を少数パラメータで近づける。

調整順：

1. 全幅、全長、全高
2. モーター中心配置
3. ガード外径と高さ
4. 中央ボディ幅、長さ、高さ
5. アーム幅と厚さ
6. 上面・下面の丸み
7. 前後左右の明確な非対称

1回の反復ごとに設定差分、6方向レンダー、比較シートを保存する。

合格条件：

- 実測項目は指定許容差内。
- 写真推定項目は±2 mmまたは±3%の大きい方を初期目標とする。
- 正面を合わせた結果として側面が悪化するなど、ビュー間の重大な矛盾がない。
- 写真傾きを機体の非対称として誤反映していない。

### P4：部品詳細と材質

目的：識別性の高い外観を追加する。

候補：

- 上下外装の段差
- 電池部、電池蓋
- 前後LED
- コネクタやスイッチ
- 脚または下面支持部
- プロペラのCW／CCW形状
- ガード支柱
- 基本色と粗さ

合格条件：

- 細部を加えてもP2、P3の寸法が変わらない。
- 材質をOFFにしても形状評価が成立する。
- LOD0が目標ポリゴン範囲を大幅に超えない。

### P5：アンカーと物理用モデル

目的：シミュレーションで力、回転、衝突を扱える状態にする。

作業：

1. 4個のモーター軸Emptyを作る。
2. 重心Emptyを作る。
3. 中央ボディ、アーム、モーター、必要なガードの衝突形状を作る。
4. 総質量、推定重心、初期慣性を設定する。
5. ローターごとの回転方向と推力軸をカスタムプロパティへ保存する。

合格条件：

- 全モーター軸のローカルZが同じ推力方向を向く。
- 対角ローターが同方向、隣接ローターが逆方向という設定が明示されている。
- 回転方向が未確認なら、正規物理モデルとして合格させない。
- 衝突形状に非多様体、負scale、極端な薄さがない。
- 質量と慣性の情報源が記録されている。

### P6：GLB出力とエンジン検証

目的：Blender外でも階層と物理用情報を利用できることを確認する。

作業：

1. `.blend`とGLBを生成する。
2. GLBを再読込みし、部品名、軸、階層、寸法を検査する。
3. Godotへ読み込み、スケールと前方向を確認する。
4. 各ローターを個別回転させるスモークテストを作る。
5. 衝突形状を可視化して確認する。

合格条件：

- GLB再読込み後の全体寸法差が0.5 mm以内。
- 4個のローターを独立回転できる。
- 前方向、上方向、重心原点が想定どおりである。
- 表示用形状と衝突用形状を区別できる。
- Godot上で不要な参照写真や評価カメラが含まれない。

## 3. 実装ファイルの優先順位

### 最小実装

```text
config/drone2_model.yaml
scripts/drone_model/run_build.py
scripts/drone_model/validate_config.py
blender/drone_model/build_drone.py
blender/drone_model/parts.py
scripts/drone_model/qa_model.py
```

最初はこれだけでP0～P2を完了させる。

### P3以降で追加

```text
blender/drone_model/references.py
blender/drone_model/collision.py
blender/drone_model/export.py
scripts/drone_model/build_contact_sheet.py
tests/drone_model/test_config.py
tests/drone_model/test_dimensions.py
tests/drone_model/test_naming.py
```

## 4. ランナーの責務

`scripts/drone_model/run_build.py`は次を行う。

1. リポジトリルートとBlender実行ファイルを解決する。
2. YAML設定を検証する。
3. 出力先が既存の場合の上書き方針を確認する。
4. Blenderをバックグラウンドで起動する。
5. stdout、stderr、終了コードを保存する。
6. Blenderの例外文字列も検査する。
7. 必須成果物の存在と更新時刻を検査する。
8. QAと比較シート生成を実行する。

既存の`pipeline_v2/p2_run.py`で得られた知見を流用し、BlenderがPython例外時にも
終了コード0を返す場合に備えて、`Traceback`と新規成果物の存在を必ず確認する。

## 5. Blenderスクリプトの責務

`blender/drone_model/build_drone.py`は次を行う。

- `--`以降の引数を解析
- 工場出荷状態または空シーンから開始
- メートル単位と座標規約を設定
- Collectionを作成
- 設定値をmmからmへ変換
- 各部品を生成
- 部品を組み立て
- アンカーとカスタムプロパティを設定
- シーン寸法と部品表をJSONへ出力
- `.blend`を保存
- 対象CollectionだけをGLBへ出力
- 6方向レンダーを生成

標準処理には`bpy.ops`を使い、部品データの正確な作成にはData APIや`bmesh`を使う。
Objectの選択状態とactive Objectを各処理で明示し、前処理の副作用へ依存しない。

## 6. 自動検査項目

### 設定検査

- 必須項目の欠落
- 負またはゼロの寸法
- プロペラ径がガード内径を超える
- ガードと隣接ガードの不正な重なり
- モーター中心がボディ内部へ入る
- `measured`なのに根拠メモがない
- 正規ビルドで`placeholder`が残る

### Blenderシーン検査

- 必須Objectの存在
- Object名の重複と`.001`
- 親子階層
- 原点位置
- ローカル軸
- 負scale
- 未適用scale
- 4ローターの中心位置
- バウンディングボックス寸法
- 表示用と衝突用Collectionの分離

### メッシュ検査

- triangles
- connected components
- non-manifold edges
- degenerate faces
- loose vertices
- 法線方向
- 材質数

表示用ガードの開いた円弧など、意図した非watertight形状はエラーにしない。
衝突形状はwatertightまたはエンジンのプリミティブ表現を必須にする。

## 7. 目視評価

`blender/drone_model/build_drone.py`の`render_views`で、
上、下、前、後、左、右の6方向を出力する。

比較シートは各行をビュー、各列を次の内容にする。

1. 元写真
2. 写真切抜き
3. 無彩色モデル
4. シルエット重ね合わせ
5. 寸法と未確定項目

シルエット差分の自動点数は補助値とする。写真の透視や部品角度が統一されていないため、
単一の画素一致率だけで合否を決めない。

## 8. MCP運用ルール

### MCPで行ってよいこと

- シーン構造と寸法の読取り
- Object、Collection、Modifier、Materialの確認
- 参照カメラへの移動
- スクリーンショットとレンダー
- 仮のプリミティブ追加による形状検討
- 設定変更候補の算出

### MCPだけで完了してはいけないこと

- 正規メッシュの手作業頂点編集
- 名前や階層を記録せず変更
- 設定へ戻していない寸法変更
- 既存成果物を直接上書きして正規版とすること

MCPセッション終了前に、採用変更が設定またはスクリプトへ反映されていることを確認する。

## 9. 既存資産の再利用

| 既存資産 | 再利用内容 |
|---|---|
| `config/drone2_model.yaml` | 6方向の入力パス、実測値、部品寸法、出力定義 |
| `config/drone_templates/` | 4ロータ互換と汎用マルチロータの標準値 |
| `blender/drone_model/build_drone.py` | 部品生成、組立、6方向レンダー、GLB出力 |
| `scripts/drone_model/run_build.py` | Blenderバックグラウンド起動、成果物検査、QA |
| `pipeline_v2/p2_run.py` | Blender例外と古い成果物を誤認しないランナー設計 |
| `blender/cleanup_export.py` | GLB出力、単位、transform処理 |

AI生成meshは新モデルへImport、Append、形状転写しない。写真と実測値だけを根拠にする。

## 10. リスクと対策

| リスク | 対策 |
|---|---|
| 絶対寸法がない | 最初にモーター中心間距離を1個実測する |
| 写真の透視が一致しない | 各ビューの補正を分離し、実測値を優先する |
| 細部作業が先行する | P2の構造ゲートを通るまで材質と小部品を作らない |
| MCP操作が再現できない | 採用変更をYAMLまたはPythonへ必ず戻す |
| Booleanで不安定になる | プリミティブ、Curve、断面押出しを優先する |
| 物理値を外観から誤推定する | 質量と重心を実測し、慣性の情報源を明記する |
| 旧成果物をPASSと誤認する | 出力時刻、ハッシュ、Traceback、必須成果物を検査する |

## 11. 推奨する最初の実装単位

次の1サイクルを最初の実装目標とする。

1. ユーザーがモーター中心間距離を1個測る。
2. Codexが`config/drone2_model.yaml`の初版を作る。
3. `body_core`、`arm_fl`、`motor_fl`、`rotor_fl`、`guard_fl`を生成する。
4. 4方向へ組み立てる。
5. `.blend`、GLB、6方向無彩色レンダーを出す。
6. Blender MCPで写真と比較する。
7. 設定値を1回修正して再生成する。

このサイクルが成立すれば、ローカル3D AIを使わずに、Codex、Blender MCP、
決定的なPythonスクリプトで1個のモデルへ仕上げる経路が成立したと判断できる。

## 12. 今回の計画判断

- ローカル3D生成AIの追加評価は行わない。
- TripoSR、Hunyuan3Dのmeshをベースモデルにしない。
- 既存写真と切抜きは参照として再利用する。
- 正規成果物はパラメータ設定とBlender Pythonから生成する。
- MCPは重要だが、再現性のため必須依存にはしない。
- 最初のブロッカーはGPUではなく、絶対スケール用の実測値である。
