> **作成:** 2026-07-10
> **背景:** B-6 で出力した `cat_koha.glb` が、(1) 前足が破綻、(2) 参照アセットのほぼそのまま、
> (3) `input/raw_photos` の猫に似ていない、という状態で失敗した。原因を実測で特定し、
> 「確実にやれる」手順に組み直す。

## 1. 現状の実測（推測ではなく計測結果）

### 1-1. 前足の破綻は「スキニングの破綻」で確定

`godot/Godot3dcat/DiagKoha.tscn` で、同一カメラ・同一マテリアルのままポーズだけ変えて撮影した。

| 条件 | 結果 | 出力 |
|---|---|---|
| レストポーズ | 前足・胸ともに完全に無傷 | `output_v2/reports/diag_koha_A_asis_rest.png` |
| Idle1 再生 | 左前足が本体から分離して破片化、右前足は切株状 | `output_v2/reports/diag_koha_A_asis_idle1.png` |

マテリアルはポーズで変化しない。よって**半透明（alphaMode BLEND）の描画順の問題ではなく、
ボーンによる変形そのものが壊れている。**

### 1-2. 定量化: 全8アニメが破綻。破綻率は正常モデルの10〜30倍

新規に `pipeline_v2/qa_skin_stretch.py` を作成した。GLB を直接読み、リニアブレンドスキニングを
再現して「レスト時に対して3倍以上に伸びた辺」の割合を測る。Blender も Godot も要らない。

```
python pipeline_v2/qa_skin_stretch.py --glb output_v2/base/cat_koha.glb
```

| モデル | 破綻した辺の割合（8アニメ中の範囲） | 判定 |
|---|---|---|
| `cat_base.glb`（無加工のヒョウ = プロのスキニング） | 0.051% 〜 0.138% | PASS |
| `cat_koha9.glb`（B-4。ヒョウのスキニングを継承） | 0.041% 〜 0.186% | PASS |
| **`cat_koha.glb`（B-6。自作ウェイト）** | **1.374% 〜 3.942%** | **FAIL** |

閾値は「破綻辺 0.5% 超で FAIL」。無加工アセットと B-4 が通り、B-6 だけが落ちるよう校正済み。
（単純な「最大伸び率」は使えない。毛カードの極小な辺のせいで無加工アセットすら x14 を記録するため。）

### 1-3. 使われているボーンが 98本中 20本しかない

| モデル | ウェイトを持つボーン | 前脚チェーン |
|---|---|---|
| `cat_base.glb` | 82 / 98 | upperarm → forearm → hand → finger0-4（指まで全部） |
| `cat_koha.glb` | **20 / 98** | **upperarm → forearm で終わり** |

`hand` / `foot` / `finger*` / `toe*` は全部ウェイトゼロ。前足は肘までしか関節がなく、
肉球から先は前腕に剛体で貼り付いている。`b6_koha9_mesh_transplant_blender.py:61` の
`LEG_CHAINS` が2関節しか定義していないことに対応する。

### 1-4. テクスチャは参照アセットとバイト単位で同一

`cat_koha.glb` に埋め込まれた2枚の画像の SHA256 は、
`input/cat2/koha9_cat/textures/` の元ファイルと完全一致した。
メッシュも 9,282頂点（元）→ 9,303頂点（出力）で、実体は素材そのもの。

**つまり B-6 では、raw_photos の猫に似せる作業は一度も行われていない。**
ユーザーの指摘は全面的に正しい。

## 2. なぜ cat_koha9.glb から cat_koha.glb へ方向転換したのか

`newplan/b_route_progress.md` の記録を時系列で追うと、原因は技術ではなく**参照基準のすり替え**だった。

1. **B-3 v2（07-08）** — 進捗メモ 61行目に
   「参照: ユーザー提供 `png/koha1-4.png`（koha9_cat **理想レンダー**）」と書かれている。
   しかし `png/koha1-4.png` は、素材 `input/cat2/koha9_cat` を Sketchfab がレンダリングした
   **素材自身の宣材画像**である。飼い猫 koha の写真ではない。
   この時点で、プロジェクトの「理想」が raw_photos から市販アセットにすり替わった。

2. **B-4（07-09）** — ヒョウメッシュを短足・丸顔に変形。スキニングはヒョウのものをそのまま
   引き継いだので健全（1-2 の表で PASS）。ただし顔はヒョウのまま残った。

3. **07-10** — ユーザーが Godot で確認し「見た目が理想と遠い・顔は絶対変えたい」と指摘。
   ここで「理想 = `png/koha1-4.png`」という誤った前提が効いた。理想が素材の宣材画像なら、
   **素材そのものを使うのが最短**という結論に必然的に到達する。それが B-6 の「A案: メッシュ移植」。

4. **B-6（07-10）** — koha9 メッシュを Leopard アーマチュアに載せ替え。
   移植先の見た目は素材そのもの（1-4）。そして移植のためのスキニングを自作した結果、破綻した（1-1〜1-3）。

方向転換そのものは、当時の前提の下では論理的だった。**前提が間違っていた。**

## 3. 失敗の根本原因（3つ）

### 原因A: 参照が写真ではなく素材の宣材画像になっていた
`png/koha1-4.png` を「理想レンダー」と呼んだ瞬間に、目標が達成不能ではなく**達成済み**に化けた。
素材をそのまま出せば「理想」と一致するからだ。raw_photos への類似は誰も測っていない。

### 原因B: 枯れた手法を捨てて幾何アルゴリズムを自作した
`b6_koha9_mesh_transplant_blender.py` は648行あり、その中核は自作のウェイト割り当てである。
Blender 標準の Automatic Weights（ボーンヒート）が「毛房の非連結パーツで全滅」したため、
距離ゲート・ガウシアンカーネル・Union-Find による毛房の剛体化・ラプラシアン平滑化を
自前で書いた（進捗メモ 116-119行目）。これが 1-2 の 1.4〜3.9% の破綻を生んだ。

自作に踏み切った判断は、その場では合理的に見える。しかし**「標準手法が通らない」は
「メッシュの前処理が足りない」のサインであって、「アルゴリズムを書け」のサインではない。**

さらに、ボーンのレスト位置を区分線形ワープでメッシュに押し込んだ（同 115行目）ため、
骨の向きとロールが解剖学的でなくなり、リターゲットした回転が破綻を増幅した。

### 原因C: 合否をスクリーンショットの印象で判定していた
B-5 も B-6 も「Godot で撮って良さそうだから完了」で閉じている。
だが **レストポーズは無傷なのだ**（1-1）。静止画1枚では、全8アニメが破綻していることを
原理的に検出できない。機械的なゲートがなかったことが、失敗を最終段階まで隠した。

## 4. 再プラン

### 4-0. 貫く5原則

1. **参照は `input/raw_photos` だけ。** 素材のレンダーを「理想」と呼ばない。
2. **幾何アルゴリズムを自作しない。** Blender 標準モディファイア（Automatic Weights /
   Data Transfer / Limit Total / Normalize All）だけで組む。標準手法が通らないときは
   前処理を直す。
3. **合否は機械が出す。** `qa_skin_stretch.py` が PASS しない成果物は「完了」と呼ばない。
4. **1フェーズ = 1つの関心事。** 骨・形・柄を同時に触らない。壊れたとき原因が特定できなくなる。
5. **撤退ラインを先に決める。** 1フェーズに2セッション以上かけない。

### P1. スキニング再構築（最重要 / ここが今回の失敗点）

`b6_koha9_mesh_transplant_blender.py` の自作ウェイト部分（`bind_mesh` 以下）を全部捨てる。
代わりに以下だけを使う。

1. **メッシュ前処理** — ここに時間を使う。標準手法が通るかどうかはここで決まる。
   - 毛シェル `Koha9Tail`（1,719頂点・alphaBLEND）を本体 `Koha9Body`（7,563頂点）から
     **別オブジェクトに分離**する。B-6 はこれを結合してから一括バインドしようとして、
     非連結な毛房112個でボーンヒートを壊した。
   - 本体に Merge by Distance → 穴埋め → 単一連結・多様体にする。
     `3D Print Toolbox` の `Check All` で non-manifold がゼロになるまで直す。

2. **アーマチュアのレストポーズを koha9 の立ちポーズに合わせる**
   - ボーンのレスト**位置**を区分線形ワープで押し込む（B-6 のやり方）のではなく、
     **ポーズモードでボーンを回転させて合わせ、`Apply as Rest Pose` する。**
     こうすれば骨のチェーン構造・向き・ロールが解剖学的なまま保たれる。
   - 元アクションはこの時点で一旦壊れる。P1 の最後にリターゲットし直す。

3. **本体を Automatic Weights でバインド。** 多様体になっていれば通る。

4. **毛シェルは `Data Transfer` モディファイア**（Vertex Group / Nearest Face Interpolated）で
   本体からウェイトをコピー → Apply。
   B-6 の「Union-Find で連結成分を数えて直下の本体からコピー」という自作コードは不要。

5. `Limit Total`（4本）→ `Normalize All`。

6. **脚は全チェーンにウェイトを持たせる**（`hand` / `foot` / `finger*` / `toe*` を含む）。
   短足だから2関節でいい、という B-6 の判断が破綻の直接原因。関節を減らすのではなく、
   アニメーション側の回転を減衰させる。

上記が **P1-A**（出力 `output_v2/base/p1a_koha.glb`）。

**P1-A 内のフォールバック（Automatic Weights がどうしても通らない場合）:**
`cat_koha9.glb`（B-4、スキニング健全）から koha9 メッシュへ `Data Transfer` で
ウェイトを転送する。骨格は同一、体型もすでに近い。衣装をキャラクターに転送するのと同じ
業界標準の操作で、レストポーズさえ揃っていれば成立する。

**P1-B**（出力 `output_v2/base/p1b_koha.glb`）は `cat_koha9.glb` をそのまま土台にする経路。
スキニングは既に健全なので P1 の作業はほぼ無く、比較対象・撤退先として同じゲートを通す。
7-1 の決定により、両経路を1セッションで並行して走らせ、数値と目視で採用を決める。

**ゲート（両方必須・両経路に同一適用）:**
- `python pipeline_v2/qa_skin_stretch.py --glb output_v2/base/<out>.glb` が **OVERALL: PASS**
- 4方向 × 8アニメ × 3フレーム のコンタクトシートを目視。破片・欠損・貫通がないこと。

**撤退ライン:** 2セッション以内に P1-A が PASS しなければ P1-B を採用し、
顔のメッシュ編集を独立フェーズとして立てる。両方 FAIL なら設計から見直す。

### P2. 尻尾（P1 の PASS 後）

B-6 は尻尾メッシュの頂点を155°の累積カーブで曲げた（`TAIL_CURL_DEG = 155.0`）。
これが背面図のトゲ状の破綻（`png/test/back.png`）を生んでいる。

代わりに、**尻尾ボーンをポーズモードで巻き上げて `Apply as Rest Pose` する。**
メッシュはスキニングで自動的に追従するので、頂点を直接触る必要がない。
`TAIL_LENGTH_SCALE` による短縮も、ボーンのスケールで行う。

**ゲート:** P1 のゲートを維持したまま、背面・側面が raw_photos の尻尾と一致すること。

### P3. 外見を koha 本人に寄せる（ここで初めて raw_photos に近づける）

7-2 の決定により2段階に分ける。**P3-1 で止めても成果物として成立させる。**

素材のテクスチャは**黒いサドルが大きすぎる**（`Koha9Body_baseColor.png` を見ると背中の大半が黒）。
koha は白優勢でオレンジ斑が散り、黒は少ない。ここを直すのが本フェーズの核心。

なお「長毛感」はテクスチャだけでは出ない。毛シェル `Koha9Tail` の押し出し量と、
必要ならノーマルマップで調整する（素材にはノーマルマップが無く、毛の陰影は
baseColor に描き込まれているだけ、という点は確認済み）。

#### P3-1. 印象合わせ（必須）

素材の 4096² baseColor を出発点に、黒サドルを削って白優勢＋オレンジ斑に置き換える。
B-3 で作ったプロシージャル三毛シェーダ（`pipeline_v2/b3_generate_calico_texture_blender.py`）と
`config/cat_color_palette.yaml` の実測パレットが流用できる。斑の正確な位置は問わない。

**ゲート:** 以下4つの特徴が揃っているかをユーザーが承認する。
白が優勢 / オレンジ斑が背・腰・顔に散る / 黒が少ない / 尻尾が太くリング柄。

#### P3-2. 位置合わせ（余力があれば）

`input/raw_photos` の斑を1対1で再現する。**写真からのマルチビュー投影ベイク。**
道具はすでにある: `blender/cat_photo_camera_projection_bake_pass.py`。

- 投影に使う写真: 真横 = `横.png`、正面 = `1750427002756.jpg`、背面 = `video_frames` から選定。
- 難所: 写真ごとの照明差（ホワイトバランス補正が要る）と、毛が動くことによる継ぎ目のズレ。
- `input/masks/reference_side_right_body_1698975320501_cutout.png` は青みの照明で
  WB が崩れているため色抽出に使えない（B-2 の知見）。投影用に写真を選び直すこと。

**ゲート:** raw_photos と同アングル・同ポーズで並べたコンタクトシートを作り、
斑の位置についてユーザーの承認を得る。「なんとなく猫っぽい」では通さない。

## 5. 常設の回帰ゲート

出力を `output_v2/base/p1a_*.glb` / `p1b_*.glb` として並置し、両方に同じゲートをかける。
**選定はゲートの数値と目視で行い、事前の思い込みで打ち切らない。**

P1-A が PASS すれば P1-A を採用（顔の問題が消えるため）。P1-A が FAIL し P1-B が PASS すれば、
P1-B を土台に顔のメッシュ編集を追加フェーズとして立てる。両方 FAIL なら設計から見直す。

### 7-2. P3 は2段階に分ける

**P3-1「印象合わせ」を先に通してモデルをいったん完成させる。** 合格条件は、
白優勢・オレンジ斑・黒少なめ・太いプルーム尻尾という特徴が揃っていること。斑の正確な位置は問わない。
プロシージャル生成または大まかな投影で到達でき、失敗リスクが低い。

**P3-2「位置合わせ」は余力があれば実施する。** `input/raw_photos` の斑を1対1で再現する。
マルチビュー投影ベイクが必須で、写真の照明差と毛の動きによる継ぎ目処理が難所になる。

各段階の終わりで個別にユーザー承認を取る。P3-1 で止めても成果物として成立する構成にする。
